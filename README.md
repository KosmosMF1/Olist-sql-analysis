# Olist E-Commerce SQL Analysis

SQL-проект по анализу данных бразильского маркетплейса Olist.

> Статус: проект находится в разработке.  
> Завершены создание базы данных и первичный анализ качества данных.

## О проекте

Цель проекта — провести полноценный анализ данных e-commerce с использованием PostgreSQL и SQL: от построения реляционной базы данных и проверки качества данных до расчёта бизнес-метрик и поиска аналитических инсайтов.

Исходные данные представлены несколькими CSV-файлами. В рамках проекта они были загружены в PostgreSQL и объединены в связанную реляционную структуру.

На текущем этапе завершён первичный анализ базы данных (`01_database_overview.sql`).

## Данные

Используется **Brazilian E-Commerce Public Dataset by Olist**.

Датасет содержит информацию примерно о 100 тысячах заказов, совершённых на бразильском маркетплейсе Olist.

## Основные результаты первичного анализа

### 1. Структура заказов

В таблице `orders` содержится:

- 99 441 строка;
- 99 441 уникальный `order_id`.

Таким образом, каждый `order_id` представлен одной строкой, и дубликатов по идентификатору заказа не обнаружено.

### 2. Пропуски в датах заказов

Большая часть пропущенных дат объясняется текущим статусом заказа.

Например, отсутствие даты доставки является ожидаемым для заказов со статусами:

- `shipped`;
- `processing`;
- `canceled`;
- `unavailable`.

При этом были обнаружены отдельные заказы со статусом `delivered`, у которых отсутствуют некоторые даты жизненного цикла заказа.

Такие записи были отмечены как потенциальные проблемы качества данных.

### 3. Уникальные и повторные покупатели

`customer_id` и `customer_unique_id` имеют различный смысл.

`customer_unique_id` позволяет идентифицировать одного и того же покупателя между несколькими заказами.

По результатам анализа:

- большинство покупателей совершили только один заказ;
- 2 997 уникальных покупателей совершили более одного заказа;
- доля покупателей с повторными заказами составляет около **3.12%**.

Распределение также показало, что отдельные пользователи совершали значительно больше заказов. Максимальное найденное количество — **17 заказов у одного покупателя**.

### 4. Цены товаров

Для `order_items.price` были проверены минимальные, максимальные и средние значения.

Получено:

- минимальная цена — `0.85`;
- максимальная цена — `6735`;
- средняя цена — около `120.65`;
- нулевых и отрицательных цен не обнаружено.

Дополнительное исследование наиболее дорогих позиций показало, что высокие цены встречаются в различных категориях, включая:

- computers;
- small appliances;
- musical instruments;
- housewares;
- art;
- game consoles.

Поэтому максимальные значения не были отнесены к очевидным ошибкам данных.

### 5. Отзывы

В таблице `reviews`:

- 99 224 строки;
- 98 410 уникальных `review_id`.

Таким образом, `review_id` не является уникальным идентификатором записи.

Было найдено 789 `review_id`, которые встречаются более одного раза, причём некоторые идентификаторы встречаются до трёх раз.

Поэтому `review_id` не был использован в качестве единственного `PRIMARY KEY` таблицы.

### 6. Платежи

В данных присутствуют следующие способы оплаты:

- `credit_card`;
- `boleto`;
- `voucher`;
- `debit_card`;
- `not_defined`.

Наиболее распространённый способ оплаты — `credit_card`.

Количество платежей:

- `credit_card` — 76 795
- `boleto` — 19 784
- `voucher` — 5 775
- `debit_card` — 1 529
- `not_defined` — 3

Отрицательных платежей обнаружено не было.

Найдено 9 платежей со значением `0`:

- 6 — `voucher`;
- 3 — `not_defined`.

Эти записи были отмечены как нетипичные, но не удалялись из данных автоматически.

### 7. Проверка составного ключа `order_items`

Для таблицы `order_items` была проверена уникальность комбинации:

```text
(order_id, order_item_id)
```

Результат:

- всего строк — 112 650;
- уникальных комбинаций — 112 650.

Следовательно, выбранный составной ключ корректно идентифицирует каждую товарную позицию заказа.

## Вывод по качеству данных

В целом данные пригодны для дальнейшего анализа.

Основные обнаруженные особенности:

- большинство пропусков объясняется бизнес-логикой статусов заказов;
- присутствуют отдельные неполные записи среди доставленных заказов;
- `review_id` не является уникальным;
- существуют несколько нулевых платежей;
- отрицательных цен и платежей не обнаружено;
- основные идентификаторы заказов и товарных позиций корректно уникальны.

Обнаруженные особенности будут учитываться при расчёте бизнес-метрик на следующих этапах.
